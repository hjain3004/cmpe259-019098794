## 1. Executive Verdict

CashBooks Assist has substantial working software and rich evaluation artifacts locally, but **the repository is not ready for public portfolio release or research submission in its current state**:

1. **Git / working-tree drift blocks external reproduction:** Remote `origin/main` (`d3c5d61`) still reflects the `v1` baseline. Local `HEAD` (`4f23435`) adds held-out `landscaping_01`, expanded development bundles (`bakery_01`, `clinic_01`, `cafe_01_x4`, `cafe_01_x16`), `v2` runs, the HTTP demo server (`demo/serve.py`), and challenge sets—while `17` modified and `23` untracked paths (including all `challenge` outputs/rescores, `lecture_metrics` / `extraction_metrics` scripts and `evaluation/results/final/` metric files, `per-run` `retrieval.md`, web UI evidence viewer changes, and `.playwright-mcp/` artifacts) are still uncommitted.

## 4. Overclaim Check

1. **"Tools beat RAG" without specifying the BM25 baseline:**  
   The evaluated RAG baselines (`C1` over raw chunks, `C2` over extracted records) use sparse **`rank-bm25`** lexical retrieval (`pyproject.toml` L11). CashBooks Assist has **not** been compared against dense embedding retrieval, hybrid sparse+dense retrieval, cross-encoder reranking, or multi-hop RAG. Any public claim must say *"outperforms sparse BM25 baselines (`C1`, `C2`)"*, not *"beats RAG"*.

2. **"Extraction has no impact" inferred from a nonsignificant difference:**  
   In `report_dev.md` (`C3` vs `C4`: `9:10`, McNemar `p = 1.000`, `95% CI [-7.0%, +5.3%]`) and on held-out `landscaping_01` (`C3` `29/40` vs `C4` `27/40`: `3:1`, `p = 0.625`, `95% CI [-4.9%, +15.0%]`), differences are small and statistically indistinguishable. Per the power table in `report_dev.md` L75–81, 80% power requires ~`14%`–`19%` differences at `60`–`120` turns. A high p-value on small synthetic bundles (`40`–`136` turns) using text-native PDFs is **inconclusive / underpowered**, not evidence that extraction errors have no impact in practice (especially on real scanned/OCR inputs).

3. **`C4` described as a guaranteed upper bound:**  
   `C4` uses human/reference-checked structured records instead of `C3`'s live extracted records, yet `C3` scores **higher** than `C4` on held-out `landscaping_01` (`29/40 = 72%` vs `27/40 = 68%`), `cafe_01_x4` (`24/28` vs `23/28`), `cafe_01_x16` (`21/28` vs `20/28`), and `v1` `plumbing_01` (`46/80` vs `44/80`). Because tool-call trajectories are stochastic, `C4` should be described strictly as a **clean-record reference configuration**, not an upper bound.

4. **"Real-world reconciliation" based only on SROIE receipt transcripts:**  
   SROIE (`626` receipts, micro-F1 `0.949` in `extraction_metrics.md`) tests **header-only NER/normalization** (`company`, `date`, `total`) on **already-OCR'd receipt transcripts**, with `3` API call failures and `32%` ambiguous-date abstentions when date-order hints are withheld (`order-none`). It does **not** exercise multi-page vendor invoices, credit notes, OCR noise, bank statement reconciliation, vendor history checks, or conversational QA.

5. **Token savings described as dollar savings:**  
   On `cafe_01_x16`, `C3` reduces `Mean tokens` from `62,973` (`C0`) to `17,053` (`-72.9%`). That metric sums tokens across turns without weighting input vs. output pricing (typically `3x`–`5x` higher per output token) or prompt-cache reuse (where `C0`'s fixed document prefix is cache-friendly while `C3` incurs repeated multi-turn tool-call loops). Moreover, at smaller bundle sizes (`cafe_01` `11,019` vs `7,872`; `plumbing_01` `11,517` vs `9,510`; `landscaping_01` `12,900` vs `9,470`), `C3` consumes **more** tokens than `C0`. Frame this as **input/context token scaling at `x16` corpus size (`62,973` -> `17,053` mean tokens)**, not universal dollar savings.

6. **`0` observed successful attacks described as general security:**  
   `0/19` ASR (`0/7` on `safety.yaml` + `0/12` on `safety_quorum.yaml`) applies strictly to deterministic checks over those fixed static prompts under `claude-haiku-5-5`. Meanwhile, `safety_failures.csv` still holds `32` automated-flag rows across configs with `0/32` human verdicts, and the suite does not test adaptive multi-turn jailbreaks, image/PDF visual attacks, non-synthetic bank feeds, or deployment auth/ACL boundaries. Say *"0/19 observed attack successes on the tested prompt/memo injection suite"*, never *"secure"* or *"immune to prompt injection"*.

7. **Rescoring described as model improvement:**  
   Challenge runs on `cafe_01` went from `8/17 (47%)` -> `14/17 (82%)` (`20261119-103951`) and `12/17 (71%)` -> `14/17 (82%)` (`20261119-110444`). Rescoring modifies deterministic/rubric grading rules on *frozen replies* (e.g., permitting an alternative duplicate-payment interpretation in `CH5 t1` or updated `CH7 t0` bounds); only the `8/17 -> 12/17` jump between `103951` and `110444` reflects a fresh run after code/prompt fixes. Any summary must distinguish **original** vs. **rescored** pass rates and explain what changed in the rubric.

8. **Multiple turns / repeats described as independent examples:**  
   - Each scenario's scored turns (`28` turns across `21` convs in `cafe_01`; `40` across `30` in `plumbing_01`/`landscaping_01`; `17` across `7` in `challenge`) are clustered within conversations and share underlying entities.  
   - `report_dev.md`'s `136` pooled turns repeat the **same `68` turns** (`2× cafe_01` + `2× plumbing_01`). While `stats.py`/`pool_report.py` properly cluster bootstrap resamples by `(scenario, query_id)`, presenting `136` turns or `x1`/`x4`/`x16` totals (`3 × 28 = 84`) as independent query counts overstates effective sample size (`N`).

## 6. Disclosure, Attribution & Provenance Flags (For User Decision)

Do **not** sanitize provenance or silently fill missing human reviews. Resolve these decisions before publication:

1. **Gold-validation wording (`project/docs/v2_evaluation_results.md` L331, `project/docs/decisions.md` L130):** Both files explicitly state that `bakery_01` and `clinic_01` gold files were checked via automated validators and *"assistant spot-checking"* / *"assistant spot-check"* rather than independent human adjudication. Decide how to word this accurately for public release (e.g., describe the deterministic validators + author checks performed) without misrepresenting unperformed human annotation as human review.
2. **Quorum red-team attribution (`project/README.md` L157, `project/docs/decisions.md` L90 D20, `project/docs/references.bib` L111):** `project/README.md` credits *"adapted from Quorum (Drexathon 2026), co-built with Dhruv J."* Confirm collaborator permission/naming preference (`Dhruv J.` vs full citation) and licensing compatibility for the selected notes in `evaluation/safety_sources/`.
3. **Unfilled human review / peer testing files:** `evaluation/review/scorer_audit_blind.csv` (`0/40`), `evaluation/review/safety_failures.csv` (`0/32`), `evaluation/results/peer_testing/summary.md` (`0` testers), and challenge human rubric columns are currently empty. Leaving them alongside active README claims risks appearing incomplete or misleading; either complete and document them genuinely or remove/explicitly mark them as *"not conducted / open work"*.
4. **Licensing & repo scope:** Neither repo root nor `project/` has a `LICENSE` file, and repo root contains course-specific folders (`class-activities/`, `homework/`, `.playwright-mcp/` scratch captures, `gold_review.html`). Decide whether to add an explicit OSS license (e.g., MIT/Apache-2.0 for original code) and whether the public portfolio release will live in a clean standalone repo/branch vs. the full course repo.

### 7D. Short Technical-Article Outline

**Working Title:** *When Do Tools Beat Context? Lessons from Building & Auditing an Accounts-Payable LLM Assistant*

1. **The Problem & Threat Model:** Why small-business bill reconciliation requires cross-document math, partial-payment disambiguation, and strict separation of untrusted vendor emails/PDF memos from verified banking records.
2. **Five Architectures (`C0`–`C4`) & Why Naive BM25 Fails:** Full raw context (`C0`), sparse `rank-bm25` over chunks/records (`C1`/`C2`), 7 typed read-only tools over extracted records (`C3`), and clean-record reference (`C4`). Why lexical retrieval collapses into over-abstention (`21%`–`56%`) while `C3` preserves grounding precision (`0.61`–`0.76`).
3. **Where Tools Help—and Where Long Context Still Competes:** Showing honest `v2` numbers—`C3` beats `C0` on `cafe_01`+`plumbing_01` (`78%` vs `68%`) and held-out `landscaping_01` (`72%` vs `62%`), trails `C0` on `bakery_01`+`clinic_01` (`57%` vs `70%`), and saves tokens at `16x` scale (`17k` vs `63k`) while costing *more* tokens at `1x` scale (`11k`–`13k` vs `8k`–`9.5k`).
4. **Why Deterministic Extraction Normalizers & UI Provenance Matter:** The SROIE `626`-receipt experiment (`0.949` micro-F1; numeric date ambiguity dropping accuracy from `99%` to `67%` without `DMY` hints) and building a clickable masked PDF/CSV evidence viewer rather than relying on unverified LLM summaries.
5. **Hard-Won Evaluation Pitfalls:** Why `C3` vs `C4` is underpowered (`p = 0.625`), why rescoring saved outputs (`47%` -> `82%`) measures rubric drift rather than model skill, why repeated runs/distractor scaling don't add independent `N`, and why human audits must actually be completed before release.
