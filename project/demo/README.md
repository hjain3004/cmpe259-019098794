# CashBooks Assist — live presentation app

This local web app connects a clean conversational interface to the existing
`ChatSession` implementation. It defaults to C3: Claude calling read-only tools
over extracted café records. The existing Streamlit app remains in `demo/app.py`.

## Run

From the project directory, using the project's existing virtual environment:

```sh
../.venv/bin/python demo/serve.py --mode live --port 8766
```

Open **http://127.0.0.1:8766**. The existing Claude provider loads its normal API
configuration when you submit the first question. Opening the page does not make
an LLM request. Each submitted live question can incur API charges. API access
and credit must be available. Stop the server with Ctrl+C.

For an offline UI rehearsal:

```sh
../.venv/bin/python demo/serve.py --mode rehearsal --port 8765
```

Open **http://127.0.0.1:8765**. Rehearsal answers and tool selections are scripted;
the listed local tools actually execute. Use the suggested questions and the
follow-ups below. Rehearsal is for layout and narration practice, not evidence of
live model performance. It makes no paid API calls.

The app uses the synthetic `cafe_01` development dataset, with the reference date
September 24, 2026. It does not connect to a real bank or initiate payments.
Relative dates such as “next seven days” refer to this dataset date.

## What the interface shows

- Plain-language answers, warnings, clarifying questions, and suggested next steps.
- Short source labels and the claims the answer cites, hidden until requested.
- **How it answered:** the tool calls actually recorded for that response, their
  arguments in readable form, and any observed tool errors. This is execution
  activity, not private model reasoning or an independent correctness check.
- **How it works:** the extraction → tools → explanation workflow, plus C0–C4
  configuration selection. Changing configuration starts a fresh conversation.
- A persistent distinction between live Claude and offline rehearsal.

Raw invoice documents, full bank-account numbers, source dumps, and tool JSON are
not displayed. Current live answers are generated by the existing assistant;
the UI does not substitute scripted answers if the live provider fails.

## Recording walkthrough (about 2–3 minutes, excluding API waits)

Use live mode at a desktop browser size around 1440 × 1000. Keep the live badge
and synthetic-data date visible at the start. Begin with **New conversation** and
**Tools + records (C3)**. Wait for each actual response before narrating its result;
the following script describes the intended demonstration, not guaranteed output.

| Scene | Action | Natural narration |
| --- | --- | --- |
| Use case, 15 s | Show the clean starting screen. | “CashBooks Assist helps a small-business owner understand bills and payments. This demonstration uses synthetic café records. The assistant can inspect records and explain them, but it cannot move money.” |
| Grounded answer, 35 s | Ask **Did I already pay invoice NS-1048?** Open **How it answered**, then close it and expand the cited sources. | “Here I am checking whether a bill has already been paid. Claude can request a Python tool that checks the recorded balance. This panel shows the calls that actually ran. The answer also identifies the records it cites.” |
| Conversation, 15 s | Ask **What date was it paid?** | “The follow-up refers to the same invoice without repeating its number. The system carries conversation context into the next request.” |
| Conflicting details, 30 s | Ask **Did the payment details on BW-771 change?** Inspect the actual answer and tool activity. | “Now I am checking a conflict between invoice payment details and the trusted vendor record. The useful behavior is to identify the discrepancy and recommend verification, rather than treating the changed account as automatically trustworthy.” |
| Boundary, 20 s | Ask **Pay it now.** | “This request is outside the assistant's capabilities. There is no payment-writing tool. The assistant should explain that boundary instead of claiming that it paid the bill.” |
| Design and limitation, 25 s | Open **How it works**. | “I separate document extraction, deterministic calculations, and language generation. C3 uses extracted records; C4 is a reference using checked records. Extraction can still be wrong or incomplete, and citations do not guarantee a correct answer. My evaluation measures those failures separately from this demonstration.” |

Optional third business task: **What bills are due in the next seven days?**
If a live answer fails, explain the observed failure and its implications. Do not
describe a scripted answer as live or claim that a short demo proves evaluation
accuracy. The test-set results, scaling curves, and safety-test outcomes belong
on separate presentation slides, with their actual denominators and limitations.

artifacts, safety tests, presentation results, or the student's ability to explain
their decisions and answer questions.

## Verification

```sh
../.venv/bin/python -m pytest code/tests/test_demo_web.py code/tests/test_demo_session.py code/tests/test_behavior_reliability.py -q
```

These checks use offline or mocked providers. They cover real local-tool execution,
follow-up context, invalid-response handling, isolated conversations, lazy live
provider initialization, safe HTTP failures, and the restricted browser payload.
They do not establish live API availability or model accuracy.
